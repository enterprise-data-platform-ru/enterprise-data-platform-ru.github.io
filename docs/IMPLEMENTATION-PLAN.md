# Enterprise Data Platform — план развития сайта для Qwen Code

**Репозиторий:** `enterprise-data-platform-ru/enterprise-data-platform-ru.github.io`  
**Домен:** https://enterprisedataplatform.ru  
**Целевая среда:** Next.js App Router, статический экспорт, GitHub Pages.  
**Исполнитель:** Qwen Code с локальной моделью Qwen 3.8 27B.  
**Базовое состояние:** аудит исходников от 25 ноября 2026 года; перед началом сверить с текущей веткой.

## 1. Цель

Развить текущий лендинг в технологический портал Enterprise Data Platform, сохранив дизайн, существующий контент, SEO, домен и возможность размещения без серверной части. Документация должна стать самостоятельным разделом с постоянными URL, боковым меню, статьями, навигацией по заголовкам, поиском и ссылками на репозитории реализации.

Не выполнять полную переработку сайта одним запросом. Каждая задача ниже — отдельная сессия, отдельный проверяемый результат и отдельный коммит после ручной проверки владельцем.

## 2. Ограничения локальной модели

Исходные параметры: контекст 32 768 токенов, максимальный ответ 4096 токенов. Это общий бюджет модели, а не гарантированный объём доступного контекста для исходников: системные инструкции, определения инструментов, история, результаты команд и ответ также занимают место.

| Правило | Значение |
|---|---|
| Цель по суммарному контексту до генерации | не более ~20–24 тыс. токенов, если счётчик доступен |
| Цель по прочитанным исходникам на задачу | 8–12 тыс. токенов суммарно, меньше при длинной истории |
| Цель по одному выводу команды | не более 150–250 строк, либо 2–4 тыс. токенов |
| Обычный размер изменения | 1–4 файла; если больше, разбить на подзадачи |
| Размер новой статьи | 400–800 слов; одна статья за сессию |
| Итоговый отчёт | до 300–500 слов |
| При приближении к 70–75% окна | остановиться на безопасной границе, записать состояние, начать новую сессию |

Эти значения — рабочие ориентиры, а не точные ограничения CLI. Если системные инструкции занимают значительную часть окна, уменьшить объём чтения. Не повышать размер окна и не менять настройки Ollama автоматически. Не рассчитывать на автокомпакцию как на замену явной передаче состояния.

### Правила чтения и редактирования

- В начале читать только `AGENTS.md`, `docs/IMPLEMENTATION-STATE.md` (если существует) и описание текущей задачи из этого плана. Не загружать весь план в каждую сессию.
- Найти нужный код через `git ls-files`, `rg -n`, `sed -n '1,160p'`, `git diff --stat`; читать только необходимые диапазоны. Не выводить содержимое `package-lock.json`, `node_modules`, `.next`, `out`, больших SVG, бинарных файлов и всей истории Git.
- Не использовать `cat` на весь `globals.css`: найти нужные селекторы и читать окружающие строки.
- Не вставлять полный вывод `npm ci`, `npm run build` и тестов в контекст: сохранять локально, передавать только последние строки и ошибки. Не считать усечённый лог доказательством успеха — проверять код возврата команды.
- Не переустанавливать зависимости при каждом шаге, если lock-файл не изменился и зависимости уже установлены. Для чистой проверки использовать `npm ci`.
- Не выполнять массовый рефакторинг, форматирование всего репозитория, обновление всех пакетов, сброс Git или публикацию без задания.
- Не исправлять смежные проблемы молча: внести их в backlog. Если возникает блокер — описать причину, минимальное решение и остановиться.
- Не создавать фиктивные работающие функции, ссылки, репозитории, версии, результаты тестов или production-гарантии.

## 3. Рабочий протокол

### 3.1. Подготовка владельцем репозитория

```bash
git status --short
git branch --show-current
git log -1 --oneline
node --version
npm --version
```

Если есть незакоммиченные изменения — не перезаписывать их. Сохранить их обычным рабочим способом с участием владельца. Создать ветку для текущего этапа, например `feat/docs-navigation`, только при чистом рабочем дереве.

Скопировать этот файл в `docs/IMPLEMENTATION-PLAN.md`. Если `AGENTS.md` уже существует, не заменять его целиком; добавить короткий блок из раздела 12 после проверки отсутствия конфликтующих правил.

### 3.2. Цикл выполнения одной задачи

1. Владелец выбирает один ID и передаёт Qwen только его описание и общий промпт из раздела 11.
2. Qwen проверяет `git status`, читает состояние и минимальный набор целевых файлов.
3. Qwen сравнивает ожидаемое и фактическое состояние. Если задача уже реализована — проверяет её и фиксирует результат вместо повторной реализации.
4. Qwen вносит минимальные изменения и целевые тесты.
5. Qwen запускает проверки; при ошибках исправляет только то, что относится к текущей задаче. Если исправление требует крупного изменения — остановиться.
6. Qwen обновляет `docs/IMPLEMENTATION-STATE.md`, если рабочая сессия не является только чтением.
7. Владелец проверяет diff, запускает необходимые команды и коммитит. Qwen не делает `git push` и не меняет настройки GitHub без явного указания.
8. Завершить сессию. Для следующего ID запустить новую сессию Qwen Code.

### 3.3. Минимальная передача состояния

Файл `docs/IMPLEMENTATION-STATE.md` должен оставаться коротким (до 60–80 строк). Он является указателем, а не журналом всех диалогов. Git хранит подробную историю изменений.

```markdown
# Implementation state

- Base commit: <git rev-parse --short HEAD>
- Current branch: <branch>
- Last completed task: <ID or NONE>
- Next task: <ID>
- Status: READY | IN_PROGRESS | BLOCKED

## Completed
- <ID>: <result>; commit: <sha or pending>

## Decisions
- <short decision and ADR path if applicable>

## Verification
- npm test: PASS | FAIL | NOT RUN
- npm run build: PASS | FAIL | NOT RUN
- npm run check:export: PASS | FAIL | NOT RUN
- Browser: PASS | FAIL | NOT RUN

## Changed files / outstanding work
- <path and remaining work>

## Blockers / deferred
- <problem and next action, or none>
```

Не записывать секреты, логи целиком, длинные фрагменты кода и вымышленные SHA. Если коммит ещё не сделан, указать `pending`.

## 5. Этап A — исправление существующего сайта

### A00 — Инвентаризация и базовая проверка

**Зависимости:** нет.  
**Читать:** `AGENTS.md`, `package.json`, `next.config.mjs`, `src/lib/paths.mjs`, `.github/workflows/ci.yml`, список файлов в `src/app` и `tests`.  
**Изменять:** только `docs/IMPLEMENTATION-STATE.md`.

- Подтвердить версии Node/Next/React по package/lock без чтения lock целиком.
- Определить фактические команды тестов и сборки, базовый путь, рабочую ветку, доступность зависимостей.
- Выполнить базовые проверки из раздела 10. Зафиксировать существующие ошибки без массовых исправлений.
- Проверить, не были ли замечания предыдущего аудита уже устранены.

**Приёмка:** состояние и блокеры записаны; исходный код не изменён.  
**Коммит:** `docs: record website implementation baseline`.

### A01 — Единый помощник для ссылок

**Зависимости:** A00.  
**Читать/изменять:** `src/lib/paths.mjs`, `tests/paths.test.mjs`.

- Сохранить `normalizeBasePath`, `basePath`, `assetPath` и существующий контракт.
- Добавить отдельную чистую функцию формирования обычного `href` с параметром префикса для тестирования. Она должна превращать `#platform` в `/#platform` при пустом basePath и `/edp/#platform` при `/edp`; `/docs/` — в `/docs/` или `/edp/docs/`.
- Не добавлять префикс к внешним HTTPS-ссылкам или `mailto:`; не допускать двойного префикса, не разрешать небезопасные URL-схемы. Определить явный контракт для входных значений.
- Не применять ручной префикс к `next/link`, если тот уже добавляет `basePath` сам. Для этой задачи сохранить существующие обычные `<a>`.

**Приёмка:** тесты пустого и непустого basePath, главной, якорей, документации и внешних ссылок проходят; старые тесты не ломаются.  
**Коммит:** `fix: centralize cross-page navigation paths`.

### A02 — Header и мобильное меню

**Зависимости:** A01.  
**Читать/изменять:** `src/components/Header.jsx`, при необходимости соответствующий фрагмент `src/content/site.mjs`; целевой тест по существующей инфраструктуре.

- CTA «Обсудить проект» направить на глобальный якорь главной.
- Добавить возможность явно пометить активный раздел документации через проп `activeSection` или аналогичный простой статический контракт; не переводить весь Header в Client Component ради подсветки.
- Если не требуется дополнительный JS, сохранить текущий `details/summary`.

**Приёмка:** из `/docs/` и с главной ссылки ведут на правильные маршруты, включая basePath. При наличии активного пункта — `aria-current="page"`.  
**Коммит:** `fix: make header navigation work across pages`.

### A04 — SEO и доступность страницы документации

**Зависимости:** A02–A03.  
**Читать/изменять:** `src/app/docs/page.jsx`, `src/app/sitemap.js`, при необходимости `src/app/layout.jsx`.

- Заменить упоминание контактной формы корректной ссылкой на контактный блок (на данный момент реализован `mailto:`; не утверждать, что адрес подтверждён).
- Сделать компактную навигационную цепочку «Главная / Документация», не добавляя несуществующих маршрутов.

**Приёмка:** правильные метаданные, sitemap, ссылка контакта, доступная структура заголовков.  
**Коммит:** `fix: improve documentation SEO and accessibility`.

### A05 — Проверка статического экспорта всех страниц

**Зависимости:** A04.  
**Читать/изменять:** `scripts/check-export.mjs`, при необходимости отдельный тест `tests/export.test.mjs`.

- Расширить существующий скрипт с одной главной страницы на HTML-файлы всего `out/`.
- Проверять внутренние `href`, локальные `src`, ссылки на страницы, assets, идентификаторы целевых якорей и соответствие basePath.
- Для маршрутов с завершающим `/` сопоставлять `index.html`. Для относительных ссылок учитывать URL исходной страницы. Игнорировать внешние URL, `mailto:`, `tel:` и неинтерпретируемые URI (например `data:`).
- Учитывать percent-encoding и HTML-экранирование; не принимать сериализованные данные внутри `script` за навигацию. Не ломать проверку Next-generated ресурсов. При необходимости выбрать небольшой HTML-парсер отдельным согласованным решением; не писать хрупкий универсальный HTML-парсер самостоятельно.
- Проверять обязательное существование `out/docs/index.html` и наличие `/docs/` в sitemap.
- Создать минимум позитивные и негативные fixtures: отсутствующая страница, отсутствующий файл, отсутствующий якорь, корневой и вложенный basePath. Обеспечить понятный ненулевой код при ошибке.

**Приёмка:** валидный экспорт проходит, битые внутренние ссылки намеренно вызывают отказ.  
**Коммит:** `test: validate links across static website export`.

### A06 — Контрольная точка навигации

**Зависимости:** A01–A05.  
**Изменять:** только состояние, если ошибок нет.

- Выполнить тесты и сборку с пустым basePath, затем с `/edp-test` как отдельную проверку.
- После тестовой сборки восстановить production-экспорт с пустым basePath.
- В браузере проверить главную, `/docs/`, логотип, каждый пункт меню, CTA и Footer при ширине ~390 и 1440 px; проверить прямую загрузку и обновление `/docs/`.
- Если браузер недоступен, отметить `NOT RUN`; не подменять ручное тестирование статическим анализом.

**Приёмка:** обе сборки и проверки экспорта проходят; ручная проверка подтверждена владельцем либо явно отложена.  
**Релиз:** отдельный PR/коммитный набор; публикация только после проверки владельцем.

## 6. Этап B — движок документации

### B01 — ADR выбора движка

**Зависимости:** A06.  
**Читать:** `package.json`, `next.config.mjs`, структуру `src/app`, соответствующий workflow.  
**Изменять:** `docs/adr/0001-documentation-engine.md`.

- Сравнить Nextra (референс AXIVO) и минимальный вариант Next.js + локальный MDX. Учесть существующий Header/Footer, собственный CSS, App Router, статический экспорт, поиск, размер зависимости и поддерживаемость.
- Проверить официальную документацию конкретных версий Next.js/Nextra/MDX, совместимость peer dependencies и `output: 'export'`. Если сети нет — не заявлять совместимость, отметить необходимость проверки.
- Предпочтительный вариант: Nextra, если он интегрируется в отдельный `/docs/` без смены дизайна главной и без серверного runtime. Иначе — Next.js + MDX, собственный небольшой layout. Не внедрять одновременно оба движка.
- Предложить точные версии только после проверки; не устанавливать пакеты в этой задаче.

**Приёмка:** ADR содержит решение, альтернативы, последствия, план PoC и условия отказа. Владелец подтверждает выбор.  
**Коммит:** `docs: record documentation engine decision`.

### B02 — Изолированный PoC движка

**Зависимости:** B01 и согласование выбора.  
**Читать/изменять:** `package.json`, lock-файл через npm, `next.config.mjs`, минимальная конфигурация MDX/Nextra и одна тестовая страница.

- Создать отдельную ветку PoC. Добавить только зависимости, необходимые выбранному движку, и одну тестовую статью (`/docs/poc/` либо согласованный временный маршрут).
- Проверить заголовки, код, статический HTML, прямой URL, basePath и отсутствие изменений главной.
- Не включать поиск, Mermaid, перевод, сложные темы и весь каталог.
- Если требуются SSR, API, runtime routing или неприемлемая смена layout — остановиться, обновить ADR и согласовать альтернативу. Не ломать рабочий сайт ради PoC.

**Приёмка:** `npm run build` и проверка экспорта проходят на обеих конфигурациях basePath; главная сохранена. PoC-страница не публикуется в main до удаления/переименования.  
**Коммит:** `feat: prototype static MDX documentation`.

### B03 — Реестр документации и маршруты

**Зависимости:** B02.  
**Читать/изменять:** новый модуль реестра (например `src/content/docs/navigation.mjs`), тесты, интеграция с механизмом маршрутизации выбранного движка.

- Определить один источник истины для slug, названия, раздела, порядка, статуса и при необходимости пути исходника. Для Nextra переиспользовать его штатную мета-структуру, если она удовлетворяет требованиям, не дублировать дерево без причины.

## 10. Проверки и технические ограничения

Команды соответствуют известному проекту; уточнить scripts в A00. В примерах `NEXT_PUBLIC_BASE_PATH` — параметр существующего `src/lib/paths.mjs`.

```bash
# Чистая установка только при необходимости или на CI
npm ci

# Тесты
npm test

# Production, собственный домен
NEXT_PUBLIC_BASE_PATH='' npm run build
NEXT_PUBLIC_BASE_PATH='' npm run check:export

# Дополнительная проверка хостинга под префиксом
NEXT_PUBLIC_BASE_PATH=/edp-test npm run build
NEXT_PUBLIC_BASE_PATH=/edp-test npm run check:export

# Восстановление production-артефакта после тестового экспорта
NEXT_PUBLIC_BASE_PATH='' npm run build
NEXT_PUBLIC_BASE_PATH='' npm run check:export

git diff --check
git diff --stat
```

Для локального браузера использовать существующий `scripts/serve.mjs` согласно `package.json`/README или подходящий статический сервер. Для проверки вложенного префикса сервер должен реально обслуживать экспорт под `/edp-test/`; обычная раздача `out/` в корне не эмулирует такой хостинг. После появления поиска использовать общую команду сборки с индексированием вместо голой сборки, если этого требует `check:export`.

При выполнении одной небольшой задачи достаточно целевого теста и, для изменений маршрутов/рендеринга, production build + export check. Полный набор обоих basePath обязателен на контрольных точках A06, B08, D04, E10, а не в каждой сессии. Не сохранять `.next`, `out`, поисковый индекс, логи и `node_modules` в Git, если существующий процесс публикации не требует иного.

Ограничения GitHub Pages:

- Сохранять `output: 'export'`, `trailingSlash: true`, совместимую конфигурацию `basePath` и статические ресурсы.
- Без SSR, ISR, Server Actions, request-dependent cookies/headers и серверных API, middleware/proxy, требующих runtime. Build-time Server Components допустимы. Dynamic routes допустимы только при полном статическом перечислении поддерживаемых путей.

- Не менять DNS, custom domain, workflow permissions, publish branch и внешние интеграции без явного разрешения.
- Не публиковать credentials, персональные данные, private repo URL или конфиденциальную документацию. GitHub Pages — публичный сайт.
- Не придумывать рабочий e-mail или endpoint формы; проверить их отдельно.

## 13. Definition of Done

Задача завершена, когда выполнены её конкретные критерии, отсутствуют незапланированные изменения, тесты/сборка имеют подтверждённый результат, состояние записано, а владелец может проверить diff и сделать коммит. При невозможности проверки задача остаётся `BLOCKED` или `IN_PROGRESS`, а не `PASS`.

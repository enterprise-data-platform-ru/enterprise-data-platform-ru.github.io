# ADR 0001 — Выбор движка документации

- **Статус:** Предложено (требуется подтверждение владельца)
- **Дата:** 2026-11-25
- **Задача:** B01 (зависит от A06)
- **Комит:** `docs: record documentation engine decision`

---

## Контекст

Сайт `enterprisedataplatform.ru` строится на Next.js 16 / React 19 (App Router, `output: 'export'`, GitHub Pages). Текущая страница документации — одиночный Server Component `src/app/docs/page.jsx`, использующий общий `Header`/`Footer` и собственный `globals.css`. Серверный runtime, API routes и middleware отсутствуют.

Нужно добавить систему технической документации (статьи, поиск, навигация по разделам) без нарушения:
- статического экспорта (`output: 'export'`, нет SSR / API);
- существующего дизайна (Header, Footer, CSS-токены);
- минимальной зависимости (GitHub Pages, `npm ci`).

Рассматриваются два варианта:

| | Nextra (референс AXIVO) | Next.js + локальный MDX |
|---|---|---|
| Суть | Готовый doc-фреймворк на Next.js | Нативная поддержка MDX в Next.js + небольшой layout |
| Layout | Свой (theme), может конфликтовать с Header/Footer | Переиспользует существующий `Header`/`Footer` |
| CSS | Присыпает собственные переменные и классы | Переиспользует `globals.css`, новые классы опциональны |
| `output: 'export'` | Поддерживается, но требует конфигурации и может тянуть SSR-опции | Родной режим, без исключений |
| Размер зависимостей | `nextra`, `next`, `react` + transitive (UI-kit, MDX) | `@mdx-js/next` или встроенный `next/mdx` (Next 16) + `gray-matter` (метаданные) |
| Поиск | Встроенный (необязательный модуль) | Добавляется отдельно, только при потребности |
| Сложность | Средняя (конфиг + переопределение темы) | Низкая (файл-конфиг + одна страница-шаблон) |

## Альтернативы

### A. Nextra

**Плюсы:**
- Готовый фреймворк, минимальный код для первой статьи.
- Встроенная структура реестра (`docs.meta.json`), breadcrumbs, TOC, поиск.
- Референс AXIVO использует Nextra — потенциальная совместимость терминологии.

**Минусы:**
- Nextra присылает собственный layout и CSS-переменные; интеграция с существующим Header/Footer требует переопределения компонентов или использования `layout` проп.
- При `output: 'export'` некоторые опции Nextra (например, `search` через `@orama` / клиентский индекс) могут требовать настройки или не работать.
- Больший объём зависимостей и транзитивных пакетов.
- Совместимость с Next.js 16 + React 19 **не проверена** в этой сессии (нет доступа к сети); требуется проверка перед PoC.

### B. Next.js + локальный MDX (рекомендуется)

**Плюсы:**
- `next/mdx` (Next 16) — встроенный, без внешних зависимостей для рендеринга.
- Layout — обычный `page.jsx` / `layout.jsx` в `src/app/docs/`, переиспользует Header/Footer и CSS-токены.
- `output: 'export'` — без исключений, без SSR.
- Минимум пакетов: `gray-matter` (если нужен YAML front-matter) + сам MDX.
- Полный контроль над разметкой, доступностью, SEO.

**Минусы:**
- Необходимо написать шаблон-обёртку, навигацию и (при необходимости) поиск вручную.
- Небольшой объём кода, не покрываемый готовым фреймворком.

### C. Markdown → статический HTML (пост-сборка)

Отклонено: нарушает модель единой сборки Next.js, требует отдельного build-шага, усложняет CI/GitHub Pages.

---

## Решение

**Рекомендуется вариант B — Next.js + локальный MDX**, при условии:

1. Пошаговый PoC (B02) проходит на `output: 'export'` в обеих конфигурациях basePath (пустой и `/edp-test`).
2. Главная страница (`/`) и текущий `docs/page.jsx` **не изменяются** до удаления/переименования PoC-страницы.
3. Nextra рассматривается, только если после PoC выявляется, что ручной MDX layout не покрывает требования.

Nextra **не выбирается** на текущем этапе, потому что:
- конфликт собственного layout с существующим Header/Footer;
- непроверенная совместимость с Next.js 16 / React 19 / `output: 'export'`;
- дополнительный объём зависимостей при минимальном функционале на старте.

---

## Последствия

**Положительные:**
- Статический экспорт сохраняется без изменений.
- Дизайн главной и документации единообразен.
- Минимальный footprint зависимостей.

**Отрицательные:**
- На начальном этапе нет встроенного поиска и TOC (добавляются отдельными задачами, если потребуется).
- Пошаговое создание layout-шаблонов увеличивает объём кода по сравнению с Nextra.

---

## План PoC (задача B02)

1. Отдельная ветка `feat/docs-poc` (от `main`).
2. Добавить `gray-matter` (опционально) и убедиться, что `next/mdx` работает.
3. Одна тестовая статья: `src/app/docs/poc/page.mdx` (или согласованный маршрут).
4. Обёртка-шаблон: `src/app/docs/layout.jsx` с Header/Footer.
5. Проверки:
   - `npm run build` + `npm run check:export` при `NEXT_PUBLIC_BASE_PATH=''` и `NEXT_PUBLIC_BASE_PATH='/edp-test'`.
   - Прямой URL к PoC-странице в обеих конфигурациях.
   - Главная страница не изменилась (сравнение DOM).
6. PoC **не публикуется** в `main` до явного согласования.

---

## Условия отказа (stop criteria)

Если в PoC выявляется **любое** из:

- Необходимость SSR, API routes или middleware для рендеринга MDX.
- Nеприемлемая смена layout или CSS-токенов главной страницы.
- Несовместимость выбранного MDX-плагина с `output: 'export'` или React 19.
- Неожиданный рост bundle / число транзитивных зависимостей > 10.

→ Остановиться, обновить ADR, согласовать альтернативу (возможно, Nextra или пересмотр архитектуры) с владельцем. Не ломать рабочий сайт ради PoC.

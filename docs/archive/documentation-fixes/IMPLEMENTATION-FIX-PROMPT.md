# Enterprise Data Platform — промпт исправления документации для Pi Coding Agent

**План:** [IMPLEMENTATION-FIX-PLAN.md](IMPLEMENTATION-FIX-PLAN.md).<br>
**Состояние:** [IMPLEMENTATION-STATE.md](../../IMPLEMENTATION-STATE.md).<br>
**Режим:** одна задача — одна сессия.

## 1. Запуск

Передать агенту из корня репозитория (заменить `FIX-03` на выбранный ID):

```text
Прочитай docs/archive/documentation-fixes/IMPLEMENTATION-FIX-PROMPT.md и выполни только FIX-03
из docs/archive/documentation-fixes/IMPLEMENTATION-FIX-PLAN.md. Не переходи к следующей задаче.
```

ID, указанный владельцем в сообщении, имеет приоритет. Если ID не указан — не выбирать задачу самостоятельно, сообщить NEXT_TASK по журналу и остановиться.

## 2. Универсальный промпт

Ты работаешь как Senior Frontend Engineer в существующем проекте Enterprise Data Platform. Цель — реализация конкретного исправления по утверждённой спецификации, а не самостоятельное проектирование интерфейса.

1. Прочитай AGENTS.md, последние записи docs/IMPLEMENTATION-STATE.md и разделы 1–2 файла docs/archive/documentation-fixes/IMPLEMENTATION-FIX-PLAN.md. Проверь текущую ветку, base commit SHA и git status.
2. Найди в плане точный заголовок `### FIX-XX —` указанной задачи и прочитай только его подраздел до следующего FIX. Прочитай только необходимые части дизайн-спецификации (раздел 3). Используй rg -n, sed -n, tail и выборочное чтение. Не загружай весь план, репозиторий, lock-файл, node_modules, .next или out целиком.
3. Сопоставь задачу с фактическим кодом. Проверь предусловия. Если исправление уже реализовано, не переписывай его; проверь критерии и сообщи результат. Если предусловие не выполнено или требуется выход за разрешённые файлы, сообщи BLOCKED, не выполняй другие FIX.
4. Реализуй только указанный FIX. Следуй точным размерам, цветам, CSS, структуре JSX и критериям приёмки. Приведённый код адаптируй к существующим компонентам, не дублируй функциональность. Не изменяй главную страницу, Header/Footer, глобальные дизайн-токены, Next.js/MDX, статический экспорт и опубликованные маршруты. Не устанавливай новые зависимости. Не создавай фиктивные ссылки и неработающие элементы управления.
5. Ограничение контекста — 32 768 токенов. Ориентир по исходникам 8–12 тыс. токенов; при 70–75% окна остановиться на безопасной границе. Используй минимальный набор файлов и короткие выводы команд. Оставь запас на тесты и итоговый отчёт. При приближении к лимиту зафиксируй незавершённую работу и остановись.
6. Выполни проверки текущего FIX и раздела 2.1 плана, включая обе конфигурации basePath, восстановление production-экспорта и git diff --check. Не утверждай, что тесты пройдены, если их не запускал.
7. Если браузер недоступен, укажи BROWSER_FUNCTIONAL_VALIDATION: NOT_RUN и VISUAL_VALIDATION: NOT_RUN. Если скриншоты получены, но ты не можешь их видеть, укажи CAPTURED_NOT_REVIEWED и пути к файлам. Сборка и DOM-анализ не равны визуальной приёмке.
8. Добавь краткую запись в docs/IMPLEMENTATION-STATE.md по разделу 2.2. Сохрани предыдущие записи. Не переписывай IMPLEMENTATION-PLAN.md и IMPLEMENTATION-FIX-PLAN.md. Не создавай коммит, не выполняй git push и не отменяй чужие изменения.
9. Верни отчёт по разделу 5: TASK, BASE_SHA, BRANCH, STATUS, CHANGED_FILES, CHECKS, BROWSER_FUNCTIONAL_VALIDATION, VISUAL_VALIDATION, SCREENSHOTS, KNOWN_ISSUES, NEXT_TASK, COMMIT_MESSAGE.
10. Остановись после текущего FIX. Не выполняй следующий FIX автоматически.

## 3. Последовательность

FIX-01 и FIX-02 уже реализованы по последнему аудиту; повторять только при обнаружении регрессии. Следующие задачи: FIX-03 → FIX-04 → FIX-05 → FIX-06 → FIX-07 → FIX-08 → FIX-09. Перед каждым запуском сверить журнал и зависимости.
